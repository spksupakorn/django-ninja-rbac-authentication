ใครเป็นเจ้าของชื่อ permission?

Permission เช่น users.read เป็น contract ระหว่าง database, service และ API guard. ถ้าทุกที่พิมพ์ string เอง ความผิดพลาดจากการสะกดต่างกันจะกลายเป็น bug ด้านสิทธิ์

Permission catalog = single source of truth

# apps/authz/permissions.py (แนวคิด)
class PermissionCode(StrEnum):
    USERS_READ = "users.read"
    USERS_UPDATE = "users.update"
    ROLES_ASSIGN = "roles.assign"

แทนที่จะให้ router เขียน "users.read", service เขียน "user.read", และ seed เขียน "users_read", ทุกจุด import value จาก catalog เดียวกัน

ผล: เปลี่ยนชื่อหรือเพิ่ม code มีจุดตรวจหลักจุดเดียว และ IDE/type checker ช่วยหา reference ที่เกี่ยวข้องได้

Code ในไฟล์ vs row ใน database

Catalog ใน Python: บอกว่า application รองรับ permission code ใดบ้าง

Permission row ใน database: ทำให้ role เชื่อมกับ code นั้นได้ และ query ได้

เราต้องมีทั้งสองอย่าง: code เป็น contract ที่ version-controlled; database row เป็น data ที่ relationships ใช้งานจริง

Seed data ผ่าน data migration

schema migration สร้าง Role, Permission, และ through tables
data migration สร้าง permission catalog เป็น rows
สร้าง role เริ่มต้น: admin, user
สร้าง RolePermission ตาม policy เริ่มต้น

Data migration ถูก commit อยู่กับ code และรันด้วย migrate. ดังนั้น local, CI และ production ได้ catalog/roles เดียวกัน ไม่ต้องให้คนเข้า database แล้ว insert ด้วยมือ

ตัวอย่าง policy เริ่มต้น

admin → ทุก permission ใน catalog
user  → permission ขั้นต่ำสำหรับผู้ใช้ทั่วไป

DEFAULT_USER_ROLE = "user"

ใน M5 เมื่อคนสมัครใหม่ AuthService จะ assign role user อัตโนมัติ โดยอ่านชื่อ default จาก settings. นี่เชื่อม registration เข้ากับ RBAC โดยไม่ hard-code policy กระจัดกระจาย

ทำไมไม่ seed ด้วยมือ?

เพิ่มมือ: แต่ละ environment อาจมี role/permission ไม่เท่ากัน, ทำซ้ำยาก, audit ไม่ชัด

data migration: ทำซ้ำได้, review ใน pull request ได้, และทุก environment มีประวัติเดียวกัน
