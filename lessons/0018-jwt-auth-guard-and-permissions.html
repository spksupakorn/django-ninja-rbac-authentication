Lesson 18 · 15 minutes

จาก Bearer token เป็น principal

M6 ทำให้ endpoint รู้ว่า caller เป็นใครและมีสิทธิ์อะไร โดยไม่ให้ทุก endpoint decode JWT ซ้ำเอง. `JWTAuth` ทำงานครั้งเดียว แล้ววาง principal ที่ตรวจแล้วไว้ใน request.auth

สิ่งที่ client ส่ง

GET /admin/users HTTP/1.1
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Bearer คือ convention ที่บอกว่า value ถัดไปเป็น credential token. อย่าส่ง refresh token ใน header นี้; protected APIs ใช้ access token เท่านั้น

JWTAuth ทำอะไร?

อ่าน access token จาก Authorization header
decode โดยกำหนด HS256 และ verify signature
ตรวจ exp ว่ายังไม่หมดอายุ
อ่าน claims: sub, roles, perms
สร้าง principal แล้วแนบเป็น request.auth
# ภาพของ request.auth
Principal(
    user_id="42",
    roles={"manager"},
    perms={"reports.read"},
)

Principal เป็นข้อมูล caller ที่ endpoint ใช้ได้โดยไม่ต้องรู้ JWT encoding details

Authentication vs authorization

Authentication: “คุณคือใคร?” — JWTAuth ตอบจาก signature/exp; failure ตอบ 401

Authorization: “คุณทำสิ่งนี้ได้ไหม?” — permission guard ตรวจ perms; failure ตอบ 403

ไม่มี token / token ปลอม / token หมดอายุ → 401
token ถูกต้อง แต่ไม่มี "roles.assign"     → 403

Permission guard

require_permission("roles.assign")
  → "roles.assign" in request.auth.perms ?
  → true: endpoint ทำงานต่อ
  → false: raise PermissionDenied → HTTP 403

Guard ไม่ query RBAC tables ทุก request เพราะ perms เป็น snapshot ใน access token. นี่เชื่อม Lesson 10 เข้ากับ JWT claims ใน Lesson 15

ทำไมแยก guard?

หาก endpoint ทุกตัว decode token และเขียน if ตรวจ permission เอง โค้ดจะซ้ำและลืม verify ได้ง่าย. Guard กลางทำให้ policy ตรวจแบบสม่ำเสมอ และ router อ่านคล้าย API contract:

@router.get("/admin/users", auth=JWTAuth())
def list_users(request):
    require_permission("users.read")(request)
    ...

syntax จริงอาจเป็น dependency/decorator ตาม implementation แต่แนวคิดคือ route ระบุ auth/permission อย่างชัดเจน
