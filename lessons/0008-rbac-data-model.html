Lesson 8 · 15 minutes

User ได้สิทธิ์ผ่าน Role

RBAC ย่อมาจาก Role-Based Access Control: เราไม่แจกสิทธิ์ให้ User ทีละข้อเป็นหลัก แต่ให้ User มี Role แล้ว Role เป็นเจ้าของชุด Permission

สี่ model ของ M2

User ← UserRole → Role
Role ← RolePermission → Permission
Permission.code เช่น users.read หรือ users.update

ลูกศรผ่าน table ตรงกลางหมายถึง many-to-many: User คนหนึ่งมีหลาย Role ได้ และ Role หนึ่งมอบให้ User หลายคนได้; Role หนึ่งมีหลาย Permission ได้เช่นกัน

เดินตามตัวอย่างจริง

User:   alice@example.com
Role:   admin
Perms:  users.read, users.update, roles.assign

UserRole:       (alice, admin)
RolePermission: (admin, users.read)
RolePermission: (admin, users.update)
RolePermission: (admin, roles.assign)

เมื่อ endpoint ต้องการตรวจ roles.assign, ระบบไม่ได้ถาม “Alice มี string นี้ไหม?” โดยตรง แต่เดิน relationship:

Alice → UserRole → admin → RolePermission → roles.assign

ทำไมไม่ใส่ list ลงใน User?

ไม่เลือก: User.permissions = ["users.read", ...] ทำให้ต้องแก้ user ทุกคนเมื่อเปลี่ยนชุดสิทธิ์ของ role

เลือก RBAC: แก้ permission ของ role เพียงครั้งเดียว แล้ว user ทุกคนที่มี role นั้นได้รับผลตาม policy เดียวกัน

ทำไมใช้ through tables ชัดเจน?

UserRole และ RolePermission เป็น table เชื่อมที่ explicit. นอกจากเชื่อมสอง model แล้ว ภายหลังสามารถใส่ข้อมูลบนความสัมพันธ์เอง เช่น วันที่ assign role, ผู้ที่ assign, หรือเหตุผลได้

class UserRole(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, ...)
    role = models.ForeignKey(Role, ...)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=["user", "role"], name="unique_user_role")
        ]

unique constraint หมายความว่า `(alice, admin)` ซ้ำสองแถวไม่ได้. เช่นเดียวกัน `(admin, users.read)` ซ้ำไม่ได้

Permission code เป็นภาษากลาง

รูปแบบ resource.action ทำให้สื่อความหมายและตรวจง่าย:

users.read
users.update
roles.assign

ใน M2 จะมี permissions.py เป็น single source of truth เพื่อไม่ให้ router, service และ data seed สะกด code คนละแบบ
