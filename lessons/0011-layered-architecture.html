Lesson 11 · 15 minutes

ทำไม router ไม่ควร query database?

โปรเจกต์นี้แยก API, service, repository และ model เพื่อให้ HTTP, business rules และ database เปลี่ยนได้โดยไม่พันกัน. โดยเฉพาะ async ORM จะถูกควบคุมไว้ในที่เดียว

สี่ชั้นและขอบเขต

API — รับ HTTP, validate input, เรียก service, ส่ง HTTP response
Service — ทำ use case และ business rule; ไม่รู้จัก request/response
Repository — เขียน async ORM query; ซ่อนรายละเอียด database
Model — นิยาม table, fields และ relationships

ตัวอย่าง: login ในอนาคต

POST /auth/login
  ↓
API router รับ JSON และ validate schema
  ↓
AuthService.login(email, password)
  ↓
AccountsRepository.aget_by_email(email)
  ↓
User model / PostgreSQL

ผลลัพธ์วิ่งกลับขึ้นเป็นลำดับย้อนกลับ: repository คืน User → service ตรวจ password/สร้าง tokens → API ส่ง JSON response

กฎที่ป้องกันโค้ดพันกัน

Router ไม่แตะ ORM: ไม่มี User.objects.filter(...) ใน endpoint

Service ไม่แตะ HTTP: ไม่มี request, status code หรือ Ninja response ใน business logic

Repository แตะ ORM ที่เดียว: query เช่น aget(), acreate() อยู่ที่นี่

เช่น service login test ได้โดยส่ง email/password ธรรมดาเข้าไป โดยไม่ต้องจำลอง HTTP request; repository test ได้แยกจาก business rule

ทำไม repository ต้องเป็น async?

# แนวคิดใน M3
user = await User.objects.aget(email=email)
new_user = await User.objects.acreate(email=email)

endpoint ของโปรเจกต์เป็น async def. การใช้ async ORM methods ใน repository ลดความเสี่ยงที่ query sync จะ block event loop หรือทำให้เกิด SynchronousOnlyOperation

หมายเหตุ: password hashing เป็นงาน CPU-bound ไม่ใช่ ORM; M4 จะห่อมันด้วย sync_to_async(..., thread_sensitive=False) ใน service. นั่นก็เป็นเหตุผลที่ขอบเขตแต่ละชั้นช่วยให้เห็นงานผิดประเภทได้ง่าย

Domain exception เดินขึ้นไปอย่างไร?

repository: ไม่พบ User
  ↓
service: raise InvalidCredentials
  ↓
API exception handler: map เป็น HTTP 401

service บอกเพียงความหมายทางธุรกิจ ไม่ผูกกับ HTTP. API layer จึงเป็นจุดเดียวที่ตัดสินว่า error ใดตอบ 401, 403 หรือ 409
