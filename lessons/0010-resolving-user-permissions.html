จาก Role หลายตัวเป็น permission set เดียว

Endpoint ไม่ควรต้องรู้ว่าผู้ใช้มี role ใดบ้างละเอียดทุกครั้ง; สิ่งที่มันต้องตอบคือ “มี permission code ที่ต้องการหรือไม่?” ดังนั้นระบบจึง resolve ความสัมพันธ์เป็นชุดของ codes

คำถามที่ระบบตอบ

user.permissions()
# ผลลัพธ์เชิงแนวคิด
{"users.read", "reports.read", "roles.assign"}

ผลลัพธ์เป็น set[str] ไม่ใช่ list เพราะ permission เดียวอาจมาจากหลาย roles แต่สำหรับการอนุญาต เราสนใจเพียงว่ามีหรือไม่มี

เดิน relation ทีละชั้น

User: Alice
UserRole → roles: manager, auditor
RolePermission → codes: reports.read, users.read, reports.read
แปลงเป็น set → {reports.read, users.read}

แม้ทั้ง manager และ auditor มี reports.read, set จะเก็บเพียงครั้งเดียว

จาก set ไปสู่ authorization decision

required = "reports.read"
allowed = required in user_permission_codes

นี่คือ logic ขั้นต่ำของ require_permission(code) ใน M6. M6 จะอ่าน codes จาก access token เพื่อเลี่ยง query database ทุก request แต่ความจริงต้นทางยังมาจาก RBAC relationships ที่เรียนใน M2

แยก concern: M2 นิยามว่า “ใครมีสิทธิ์อะไร” ใน database; M6 นิยามว่า “HTTP request นี้ผ่านหรือไม่”. ทั้งคู่ใช้ code contract เดียวกัน

ทำไมไม่เก็บ permissions บน User โดยตรง?

การ resolve ตอนต้องใช้ทำให้ role เป็น source ของ policy ตาม RBAC. User ที่ได้ role ใหม่หรือ role ที่ถูกปรับ policy จะได้ผลของ relationship โดยไม่ต้องเขียน list permissions ใหม่ใส่ทุก User

ความสดของข้อมูลและ JWT

เมื่อ M4/M6 ใส่ roles และ permissions ลง access token, request ต่อ ๆ ไปจะใช้ snapshot ใน token จน token หมดอายุ (แผนกำหนด 15 นาที). จึงมี trade-off: request เร็วขึ้น แต่การเปลี่ยน role ไม่สะท้อนทันทีใน token เก่าทุกใบ

ลองอธิบายกลับ

ถ้า Alice มี roles สองตัว และทั้งสองให้ reports.read, permission set สุดท้ายควรมี reports.read กี่ครั้ง? และเหตุใด?
