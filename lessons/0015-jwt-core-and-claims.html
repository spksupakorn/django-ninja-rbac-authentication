JWT คือบัตรที่ server เซ็นให้

หลัง login สำเร็จ server ออก JWT ให้ client ส่งกลับมากับ request ต่อไป. Server ตรวจ signature และ claims ได้โดยไม่ต้อง query database ทุก request เพื่อรู้ว่า token ถูกออกโดยระบบและยังใช้ได้หรือไม่

โครงสร้างสามส่วน

header.payload.signature

Header: metadata เช่น algorithm HS256

Payload: claims เช่น user id และเวลาหมดอายุ

Signature: หลักฐานว่าข้อมูลถูกเซ็นด้วย secret ของ server และไม่ถูกแก้

สำคัญ: payload เป็น Base64URL encoding ไม่ใช่ encryption. ใครที่มี token อ่าน payload ได้ จึงห้ามใส่ password, JWT secret หรือข้อมูลลับในนั้น

HS256 ใช้ secret อย่างไร?

token = jwt.encode(payload, JWT_SECRET, algorithm="HS256")
claims = jwt.decode(token, JWT_SECRET, algorithms=["HS256"])

HS256 เป็น symmetric signing: server ที่ออก token และ server ที่ verify token ต้องมี JWT_SECRET เดียวกัน. ถ้าแก้ payload เช่น เพิ่ม permission แต่ไม่มี secret ที่ถูกต้อง signature จะ verify ไม่ผ่าน

Claims ของ access token

{
  "sub": "42",
  "exp": 1760000900,
  "iat": 1760000000,
  "jti": "unique-token-id",
  "roles": ["manager"],
  "perms": ["reports.read"]
}
  • sub (subject): identity ของ user; โดยทั่วไปส่ง user ID เป็น string
  • exp (expiration): หลังเวลานี้ token ใช้ไม่ได้
  • iat (issued at): เวลาที่ server ออก token
  • jti (JWT ID): identifier ของ token ใบนี้ ใช้ประโยชน์กับการติดตาม/revocation
  • roles, perms: snapshot จาก RBAC ที่ M2 สร้างไว้

Decode ต้อง verify เสมอ

# ถูก: ระบุ algorithm ที่ยอมรับ และให้ library verify signature/exp
jwt.decode(token, JWT_SECRET, algorithms=["HS256"])

# ผิด: อ่าน payload โดยไม่ verify แล้วเชื่อข้อมูลในนั้น

เมื่อ signature ผิดหรือ exp หมดอายุ PyJWT จะ raise error; JWT layer แปลงมันเป็น domain error แทนที่จะให้ endpoint แต่ละตัวจัดการเอง

สิทธิ์ใน token เป็น snapshot

เพราะ access token มี perms อยู่แล้ว M6 สามารถตรวจ permission ได้เร็วโดยไม่ query database ทุก request. Trade-off คือหาก admin เปลี่ยน role วันนี้ token เก่าจะยังมี snapshot เดิมจนหมดอายุ; แผนตั้ง access TTL ไว้ 15 นาทีเพื่อลดช่วงนี้

Quiz: JWT ที่ signed ด้วย HS256 ปกป้อง payload ในเรื่องใดเป็นหลัก?

ลองอธิบายกลับ

ทำไม client จึงอ่าน payload ของ JWT ได้ แต่ยังไม่ควรแก้ perms ใน token เอง? อธิบายด้วย role ของ signature และ JWT_SECRET
