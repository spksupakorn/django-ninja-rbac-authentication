Lesson 19 · 12 minutes

ทำไม login ต้องมี rate limit?

Argon2 ทำให้การเดา password หนึ่งครั้งมีต้นทุน แต่ attacker ยังส่ง request ซ้ำจำนวนมากได้. Throttling จำกัดจำนวนครั้งที่ endpoint sensitive ถูกเรียกในช่วงเวลาเพื่อช่วยลด brute-force และ credential stuffing

Policy ใน ADR

THROTTLE_LOGIN = "5/minute"

ป้องกัน:
POST /auth/login
POST /auth/refresh

ความหมายคือ IP หนึ่งเรียก endpoint ประเภทนี้ได้ไม่เกิน 5 ครั้งต่อหนึ่งนาทีตาม policy ที่ M6 จะ implement. เมื่อเกิน ต้องตอบ 429 Too Many Requests แทนที่จะรัน password/token validation ต่อ

ไม่ใช่แค่ password ผิด

Brute-force: ลอง passwords หลายค่าใน account หนึ่ง

Credential stuffing: ลอง email/password pairs ที่รั่วมาจากระบบอื่นจำนวนมาก

Refresh abuse: ทดลองหรือยิง refresh endpoint ซ้ำอย่างรวดเร็ว

จึง throttle ที่ขอบ API ก่อนงาน expensive อย่าง Argon2 verify และ database lookup มากเกินไป

Flow ของ request

รับ IP และระบุ endpoint ที่ต้อง limit
ตรวจ counter ใน time window
ถ้ายังเหลือ quota → รัน AuthService
ถ้าเกิน quota → 429 โดยไม่เรียก AuthService

การ limit ต่อ email เพิ่มเติมช่วยกรณี attacker กระจาย request ผ่านหลาย IP เพื่อโจมตี account เดียว; ADR ระบุให้เพิ่มเมื่อ implement

401 vs 429

password/token ไม่ถูกต้อง → 401
token valid แต่ไม่มี permission → 403
เรียก endpoint เกิน rate limit → 429

429 ไม่ได้บอกว่า credentials ถูกหรือผิด; มันบอกว่า client ต้องชะลอการส่ง request

ข้อจำกัดของ in-memory throttle

web instance A: counter IP X = 5
web instance B: counter IP X = 0

ถ้ามีหลาย server แต่ละ process มี memory ของตนเอง attacker อาจสลับไปยิงหลาย instances แล้วหลบ limit ได้. สำหรับ Phase 1 ยอมรับข้อจำกัดนี้เพื่อลด infrastructure; Phase 2 ควรใช้ shared backend เช่น Redis

อย่ามอง throttle เป็นการป้องกันชั้นเดียว: มันทำงานร่วมกับ Argon2, generic login errors และ dummy verify ที่เรียนมาแล้ว
Quiz: login ถูกเรียกเกิน 5 ครั้ง/นาทีจาก IP เดียว ควรตอบ status ใด?

A = 429 · B = 401 · C = 403
