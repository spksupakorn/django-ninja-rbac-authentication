Lesson 13 · 12 minutes

Business failure ไม่ใช่ HTTP response

เมื่อ service พบว่า login ไม่ถูก, email ซ้ำ หรือไม่มีสิทธิ์ มันควรส่ง “ความหมายของปัญหา” ออกมา ไม่ใช่สร้าง JSON/HTTP response เอง. API layer เป็นผู้แปลความหมายนั้นให้ client

Domain exception คืออะไร?

# apps/common/exceptions.py (แนวคิด)
class InvalidCredentials(Exception): pass
class TokenReused(Exception): pass
class PermissionDenied(Exception): pass
class EmailAlreadyExists(Exception): pass

ชื่อ exception บอกกติกาธุรกิจที่ล้มเหลว. มันไม่พูดถึง HTTP, JSON, Ninja หรือ status code จึงใช้ซ้ำได้จาก API, CLI หรือ background task

ตัวอย่าง register flow

API router → AuthService.register(email, password)
              ↓
        พบ email ซ้ำ
              ↓
        raise EmailAlreadyExists
              ↓
Ninja exception handler → HTTP 409 {"detail": "Email already exists"}

Service ไม่ return Response(..., status=409). การ map 409 อยู่ที่ exception handler กลาง ซึ่งทำให้ทุก endpoint ตอบ format เดียวกัน

Mapping ของโปรเจกต์

InvalidCredentials → 401 Unauthorized

PermissionDenied → 403 Forbidden

EmailAlreadyExists → 409 Conflict

TokenReused → 401 Unauthorized

401 หมายถึง identity/credentials ใช้ไม่ได้; 403 หมายถึงรู้ว่า caller คือใคร แต่เขาไม่มี permission ที่ต้องใช้

ข้อดีของ handler กลาง

Service ทุกตัว raise exception แบบเดียวกัน
API มี mapping status code อยู่จุดเดียว
client ได้ error JSON รูปแบบสม่ำเสมอ
เปลี่ยน HTTP format ไม่ต้องแก้ business logic

Security: อย่าเปิดข้อมูลเกินจำเป็น

ตอน login, ไม่ว่า email ไม่มีจริงหรือ password ผิด service ควร raise InvalidCredentials เดียวกัน และ API ตอบ 401 แบบกลาง ๆ. ไม่ควรบอกว่า “email นี้ไม่มีในระบบ” เพราะช่วย attacker เดา account ที่มีอยู่ได้

แยกความรับผิดชอบ: service ตัดสินว่า failure คืออะไร; API handler ตัดสินว่าจะเปิดเผย message ระดับใดให้ client เห็น

ลองอธิบายกลับ

เหตุใด login ที่ email ไม่พบและ password ผิดจึงควรตอบ InvalidCredentials เหมือนกัน แทนที่จะบอก client ว่าเกิดกรณีใด?

แหล่งหลัก: ADR 0003 ของโปรเจกต์ และ ADR 0006 ของโปรเจกต์
